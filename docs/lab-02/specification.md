# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a working Requester-facing ticketing MVP: a Requester (simulated via a
Development Requester selector) can create an IT support ticket with
attachments, receive an official Ticket Number, find that ticket in My
Tickets, and inspect or manage its attachments — all scoped strictly to their
own tickets and built on the reusable Zen Green UI foundation.

## 2. Stakeholder Request Interpretation

The IT department needs a self-service intake experience before any
authentication exists. Requesters must be able to submit tickets with enough
structured detail (category, related system, priority, description,
evidence) for IT Staff to act on later, and must be able to track and manage
what they submitted. Because real login is a Lab 3 concern, a temporary
identity-selection mechanism stands in for "who is asking" without
pretending to be secure.

## 3. Scope

### Included
- Development Requester Selection screen (testing identity mechanism)
- Create Ticket (form, validation, attachment upload, ticket number generation)
- My Tickets (search, filter, sort, pagination, ownership-scoped)
- Requester Ticket Detail (read-only ticket info + attachment management)
- Attachment lifecycle: upload, metadata retrieval, download, soft removal
- Zen Green reusable UI foundation (forms, badges, lists, states)

### Excluded
- Authentication: login, logout, passwords, sessions, tokens, real
  role-based authorization
- IT Staff dashboard, ticket claiming/reassignment, IT Priority changes
- Public Comments, Internal Notes, Actions Taken
- Any status transition beyond the initial `New` status
- Administrator functions (user/reference-data management)

## 4. Functional Requirements

- FR-01 The system provides a Development Requester Selection screen listing
  only active Development Requesters.
- FR-02 The selected Development Requester persists as the active context
  until explicitly changed via "Change Requester".
- FR-03 A Requester can create a Ticket by submitting Category, Related
  System, Summary, Description, and Requested Priority.
- FR-04 A Requester can attach 0–5 supporting files (JPG/JPEG/PNG/WEBP/PDF,
  ≤5 MB each) during ticket creation.
- FR-05 On successful creation, the backend generates and returns a unique,
  human-readable Ticket Number.
- FR-06 A Requester can view a paginated list of only their own Tickets in
  My Tickets.
- FR-07 A Requester can search My Tickets by Ticket Number or Summary text.
- FR-08 A Requester can filter My Tickets by Category, Requested Priority,
  and Current Status.
- FR-09 A Requester can sort My Tickets by Created Date, Last Updated, or
  Ticket Number, ascending or descending.
- FR-10 A Requester can open a Ticket Detail screen for any Ticket they own.
- FR-11 The Ticket Detail screen displays all header fields as read-only.
- FR-12 A Requester can add a permitted attachment to an existing owned
  Ticket, subject to the 5-active-attachment limit.
- FR-13 A Requester can download an active attachment on an owned Ticket.
- FR-14 A Requester can soft-remove their own attachment on an owned Ticket,
  providing a removal reason.
- FR-15 A removed attachment remains visible as metadata on the Ticket but
  cannot be downloaded or previewed.
- FR-16 The system rejects any attempt to view, list, or modify a Ticket or
  Attachment not owned by the currently selected Requester.

## 5. Business Rules

- BR-01 The official Ticket Number is generated by the backend and must be
  globally unique. Format: `TKT-{creation year}-{6-digit zero-padded,
  globally sequential, based on the Ticket's database id}` (e.g.
  `TKT-2026-000042`). The client never supplies or edits this value.
- BR-02 A new Ticket always begins with Current Status `New`. No other status
  is reachable within Lab 2 scope.
- BR-03 Lab 2 uses a Development Requester selector instead of login. The
  selected identity is for testing only and is not authentication; no
  password, session, or token is created or checked.
- BR-04 Ticket Date, Ticket Owner, and IT Priority are system-managed or
  deferred fields: Ticket Date is set to server time at creation; Ticket
  Owner and IT Priority remain unset (`null`) until a later lab introduces
  IT Staff assignment.
- BR-05 Only Development Requesters with `isActive = true` appear in the
  Development Requester Selection dropdown.
- BR-06 Switching the selected Requester immediately invalidates any
  previously loaded My Tickets / Ticket Detail data; the UI must reload
  Requester-scoped data after a switch.
- BR-07 A Ticket's `requesterId` is fixed at creation and is never
  reassigned within Lab 2 scope.
- BR-08 My Tickets returns only Tickets whose `requesterId` matches the
  currently selected Requester. This filter is enforced server-side, not
  only in the UI.
- BR-09 Default sort order for My Tickets is Created Date descending
  (newest first) when no sort parameter is supplied.
- BR-10 Default page size is 10; the client may request up to 50 per page;
  values outside 1–50 are clamped, not rejected.
- BR-11 Summary must be 5–120 trimmed characters; Description must be
  10–2000 trimmed characters. Both are required.
- BR-12 Category and Related System must reference an existing, active
  record; submitting an inactive or unknown id is rejected with a 400.
- BR-13 Requested Priority must be one of `LOW`, `MEDIUM`, `HIGH`; it is
  required and has no default.
- BR-14 The Create Ticket form disables its Submit button for the duration
  of the request to prevent duplicate submissions from repeated clicks.
- BR-15 If ticket creation fails (validation or server error), no partial
  Ticket is persisted, and all form field values entered by the Requester
  are retained in the UI so nothing needs to be re-typed.
- BR-16 If the Ticket record is created successfully but one or more
  attached files fail to upload, the Ticket is still saved and returned
  with its Ticket Number; the response lists which attachments succeeded
  and which failed, and the Requester may retry the failed ones from the
  Ticket Detail screen (attachment upload is not part of the same
  all-or-nothing transaction as the Ticket record itself).
- BR-17 Attachment type is validated by both file extension and declared
  MIME type; a mismatch between the two is rejected.
- BR-18 Attachment storage uses a generated, collision-resistant stored
  filename (not the user-supplied original name) to prevent path traversal
  or overwrite; the original filename is retained as display metadata only.
- BR-19 The 5-active-attachment limit is enforced server-side per Ticket and
  counts only attachments where `removedAt` is null.
- BR-20 Soft removal sets `removedAt` (timestamp) and `removedReason`
  (required, 3–200 characters) on the Attachment; the row is never deleted.
- BR-21 Only the owning Requester may soft-remove an attachment on their
  own Ticket; the backend re-checks ownership on every attachment action,
  not just on the parent Ticket fetch.
- BR-22 An inactive Development Requester cannot be selected going forward,
  but Tickets they already created remain visible and manageable if they
  were active at the time of selection (i.e. inactivation does not affect
  Tickets created earlier in the same session).
- BR-23 My Tickets shows an explicit "no results" state when filters/search
  produce zero matches on an otherwise non-empty ticket set, distinct from
  the "empty" state shown when the Requester has zero Tickets at all.
- BR-24 Ticket Detail access to a Ticket id that exists but belongs to
  another Requester returns 404 (not 403), to avoid revealing that the
  Ticket exists.
- BR-25 In Lab 3, the Development Requester selector will be replaced by
  real authentication; `requesterId` will be derived from the authenticated
  session rather than client-supplied context, and this data model is
  designed so that swap does not require a schema change to `Ticket`.

## 6. UI Specification Summary

See `ui-spec.md` for the full specification. Summary: the application shell
uses the Zen Green palette (primary `#006B3C`) with persistent navigation
(TokTickIT title, My Tickets, Create Ticket, current Requester display with
Change Requester action). Create Ticket is a single-column form on mobile
and a grouped multi-section layout on desktop, with read-only
system-generated fields visually distinguished from editable fields. My
Tickets renders as a filterable/sortable table on desktop and stacked cards
on mobile. Ticket Detail is a read-only header block plus a dedicated
Attachments panel. All screens implement loading, empty, no-results
(where applicable), success, and error states per the Zen Green states
table.

## 7. Data Changes

New Prisma models (in addition to the existing `Category` from Lab 1):

```prisma
model DevelopmentRequester {
  id        Int      @id @default(autoincrement())
  name      String
  email     String   @unique
  isActive  Boolean  @default(true)
  createdAt DateTime @default(now())
  tickets   Ticket[]
}

model RelatedSystem {
  id        Int      @id @default(autoincrement())
  name      String   @unique
  isActive  Boolean  @default(true)
  createdAt DateTime @default(now())
  tickets   Ticket[]
}

enum RequestedPriority {
  LOW
  MEDIUM
  HIGH
}

enum TicketStatus {
  NEW
  // OPEN, IN_PROGRESS, RESOLVED, CLOSED, CANCELLED reserved for later labs
}

model Ticket {
  id                Int                   @id @default(autoincrement())
  ticketNumber      String                @unique
  requesterId       Int
  requester         DevelopmentRequester  @relation(fields: [requesterId], references: [id])
  categoryId        Int
  category          Category              @relation(fields: [categoryId], references: [id])
  relatedSystemId   Int
  relatedSystem     RelatedSystem         @relation(fields: [relatedSystemId], references: [id])
  summary           String
  description       String
  requestedPriority RequestedPriority
  itPriority        RequestedPriority?
  currentStatus     TicketStatus          @default(NEW)
  ticketOwnerId     Int?
  createdAt         DateTime              @default(now())
  updatedAt         DateTime              @updatedAt
  attachments       Attachment[]

  @@index([requesterId])
  @@index([categoryId])
  @@index([currentStatus])
}

model Attachment {
  id               Int       @id @default(autoincrement())
  ticketId         Int
  ticket           Ticket    @relation(fields: [ticketId], references: [id])
  originalFileName String
  storedFileName   String    @unique
  mimeType         String
  sizeBytes        Int
  uploadedAt       DateTime  @default(now())
  removedAt        DateTime?
  removedReason    String?

  @@index([ticketId])
}
```

Indexes: `requesterId` and `categoryId` on `Ticket` support ownership
filtering and category filtering; `currentStatus` supports status filtering;
`ticketId` on `Attachment` supports fetching a Ticket's attachments.
`ticketNumber` and `Attachment.storedFileName` are unique to prevent
collisions.

## 9. Acceptance Criteria

- AC-01 Given valid Ticket data and no attachments, when the Requester
  submits Create Ticket, then one Ticket is saved with status `New` and the
  generated Ticket Number is displayed.
- AC-02 Given valid Ticket data and 2 valid attachments, when the Requester
  submits, then the Ticket and both attachments are saved and shown as
  active in Ticket Detail.
- AC-03 Given no Development Requester is selected, when the user attempts
  to open My Tickets or Create Ticket, then the Requester Selection screen
  is shown instead.
- AC-04 Given the Summary field is empty, when the Requester submits Create
  Ticket, then a field-level validation message appears and no API call is
  made.
- AC-05 Given a 6 MB file is selected as an attachment, when the Requester
  attempts to add it, then a clear error is shown and the file is not
  uploaded.
- AC-06 Given a `.exe` file is selected as an attachment, when the Requester
  attempts to add it, then it is rejected with a clear message.
- AC-07 Given 5 active attachments already exist on a Ticket, when the
  Requester attempts to add a 6th, then the addition is rejected with a
  clear message.
- AC-08 Given the backend is unreachable, when the Requester submits Create
  Ticket, then a safe error state is shown and all entered field values
  remain in the form.
- AC-09 Given Requester A is selected and has 3 Tickets, when My Tickets
  loads, then exactly those 3 Tickets are shown and no Ticket belonging to
  another Requester appears.
- AC-10 Given Requester A is selected, when the user switches to Requester
  B via Change Requester, then My Tickets reloads and shows only Requester
  B's Tickets.
- AC-11 Given a search term matching no Ticket, when applied in My Tickets,
  then a "no results" state is shown, distinct from the empty-list state.
- AC-12 Given a Requester with zero Tickets, when My Tickets loads, then an
  empty state (not "no results") is shown with a Create Ticket call to
  action.
- AC-13 Given more Tickets than one page, when the Requester pages forward,
  then the next set of Tickets loads and pagination controls reflect the
  current page.
- AC-14 Given Requester B is selected, when a Ticket id belonging to
  Requester A is requested via the API or by opening its Ticket Detail URL,
  then the Ticket data is not returned (404) and the UI shows a not-found
  state.
- AC-15 Given an owned Ticket with an active attachment, when the Requester
  clicks download, then the original file is retrieved.
- AC-16 Given an owned Ticket with an active attachment, when the Requester
  soft-removes it with a reason, then the attachment shows as removed,
  remains visible as metadata, and its download control is disabled.
- AC-17 Given a removed attachment, when the Requester (or anyone) attempts
  to download it directly via its API endpoint, then the request is
  rejected (404/410), not served.
- AC-18 Given the Development Requester API is unreachable, when the
  Requester Selection screen loads, then a safe error state is shown with a
  retry option, not an unhandled crash.
- AC-19 Given zero active Development Requesters exist, when the Requester
  Selection screen loads, then an empty state explaining the situation is
  shown instead of an empty dropdown.
- AC-20 Given a desktop, tablet, and mobile viewport, when Create Ticket,
  My Tickets, and Ticket Detail are rendered, then no label is clipped, no
  message overlaps another element, and no horizontal page scrolling
  occurs.

## 11. Assumptions and Decisions

- Ticket Number format (`TKT-{year}-{6-digit id}`) was not specified by the
  stakeholder; a sequential, globally-unique, human-readable format was
  chosen over a random one so Ticket Numbers stay sortable and predictable
  for testing.
- IT Priority and Ticket Owner are modeled now (nullable) rather than added
  in a later migration, to avoid a breaking schema change when IT Staff
  workflow arrives, per BR-04.
- Attachment upload failure does not roll back the Ticket (BR-16): the
  stakeholder request treats Ticket creation and evidence attachment as
  related but separable concerns, and failing an entire ticket submission
  over one bad file would be poor UX.
- 404 (not 403) is used for cross-Requester Ticket access (BR-24) to avoid
  confirming a Ticket's existence to a Requester who does not own it.
